# Database migration baseline

`V1__repository_derived_baseline.sql` creates a fresh PostgreSQL schema from the
JPA metadata currently tracked in this repository. Flyway applies that baseline
and all forward migrations at application startup; CI exercises the same path
through Testcontainers PostgreSQL before Hibernate validates the mappings.

Automatic baselining is disabled. A non-empty database without
`flyway_schema_history` therefore fails closed instead of silently being marked
compatible or replaying V1.

## Fresh local database

Create an empty database, configure the values documented in
`docs/configuration.md`, then run:

```bash
cd backend
./mvnw spring-boot:run
```

Flyway records checksums and will not replay an applied migration. Never edit an
applied migration; add the next numbered, forward-only file.

## Existing environments

Do not execute V1 or automatically baseline an existing environment. Before a
production baseline marker is approved, the database owner must:

1. take an authoritative schema-only dump and record its checksum;
2. reconcile tables, columns, types, defaults, constraints, and indexes against
   V1, documenting every difference;
3. run orphan and duplicate preflight queries for every intended relationship
   or uniqueness constraint;
4. take a verified backup and rehearse restoring it;
5. test the marker and every forward migration on a representative copy; and
6. record the approved migration metadata and checksum.

Schema changes are forward-only `V2__...sql`, `V3__...sql`, and later files.
Use expand/backfill/compatibility/constraint/cleanup steps. Do not edit a file
after an environment has adopted its checksum.

## Known assumptions

- The source is repository metadata, not a deployed database dump.
- PostgreSQL-specific `jsonb` and `varchar[]` mappings are required.
- UUID values are generated by the application, so no database UUID extension
  or column default is created.
- ORM cascades are not represented as database `ON DELETE CASCADE` actions.
- `food_logs.user_id`, `user_nutrient_preferences.user_id`, and the string IDs
  in `habit_entity` are scalar mappings and therefore have no inferred foreign
  keys.
- No indexes beyond primary-key and unique-constraint indexes were inferable.
